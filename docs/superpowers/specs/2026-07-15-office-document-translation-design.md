# 飞书办公文件翻译一期设计

## 1. 背景与目标

DC-Agent 飞书小助手已经具备“办公 → 处理文件”的三步式侧面工作台、真实文件上传、飞书云文档关联、正常 LLM 路由，以及 Word、Excel、PDF、文本和飞书云文档交付能力。本期在这条现有链路中增加真实可用的“翻译”处理方式，而不是增加提示词模板或空按钮。

本期目标是：用户先提供材料，再选择翻译任务和翻译条件，最后选择真实可生成的交付格式并直接执行；系统使用 AIHubMix 上的 Qwen-MT 翻译文字，使用本地格式解析器和渲染器保留文档结构，生成可下载文件，并保存可追溯的翻译记录。

## 2. 已确认产品边界

### 2.1 本期包含

- 本地上传文件、飞书云文档、明确的 HTTPS 文件 URL。
- 待翻译源文件支持 `.docx`、`.xlsx`、`.txt`、`.md` 和可搜索 `.pdf`；`.csv` 仅作为术语表或翻译记忆输入。
- 单向翻译作为默认主流程。
- 双向互译作为高级能力，不作为默认主流程。
- 仅译文和原文/译文双语对照。
- 忠实翻译和专业润色。
- 通用、市场营销、合同法务、财务、技术和自定义专业领域。
- 可选术语表、翻译记忆和补充风格要求。
- 尽量保留原结构和商务简洁重排。
- 真实 Word、Excel、PDF、文本和飞书云文档交付；只展示当前材料实际可以生成的格式。
- 无人工审核节点；成功后直接交付，不满意时补充要求并重新生成。
- 来源、语言方向、翻译方式、模型、交付文件和重新生成关系的追溯记录。

### 2.2 本期不包含

- 图片文件翻译。
- 扫描 PDF 的 OCR、背景修复和原位置回绘。
- PDF 像素级锁版。
- `.xls`、`.xlsm`、PPT、宏、ActiveX、SmartArt、复杂文本框和嵌入对象的可靠重建。
- 任意自定义排版设计器。
- 把翻译引擎作为 MCP 服务对外发布。
- 多人协同审校或人工审核节点。

图片和扫描 PDF 后续作为独立的“图片/扫描件翻译”能力开发，复用本期的语言、术语和 Qwen-MT 调用层，但另建 OCR、版面定位、背景修复和文字回绘链路。

## 3. 用户流程

翻译继续使用统一的三步顺序，不新增平行工作流导航。

### Step 1：提供材料

用户可以：

- 上传本地文件；
- 选择飞书云文档；
- 粘贴一个明确的 HTTPS 文件 URL。

每项材料标记为“待翻译文件”“术语表”或“参考译文”，默认角色是待翻译文件。术语表和参考译文只作为专业条件，不生成对应交付文件。术语表或翻译记忆使用 `.xlsx` 或 `.csv`，前两列分别为源文和目标译文，第三列可选填写领域或备注。

系统在进入下一步前校验至少存在一项真实的待翻译文件。上传或下载后立即执行格式、大小、加密状态和可提取性预检，但此时不调用翻译模型。

### Step 2：选择和描述翻译任务

文件处理方式增加“翻译”。用户选择翻译后显示：

- 翻译方向：单向翻译（默认）或双向互译（高级）；
- 源语言：自动识别（默认）或手动指定；
- 目标语言：单向翻译时必选；
- 语言对：双向互译时必选，例如中文 ⇄ 英文；
- 译文呈现：仅译文或原文/译文对照；
- 翻译方式：忠实翻译或专业润色；
- 专业领域；
- 术语表或参考译文；
- 翻译范围，例如指定页、章节或工作表；
- 其他要求。

双向互译定义为：在一个由两种语言组成的混合文档中，系统逐翻译单元识别语言，并将语言对一侧的内容翻译为另一侧。双向模式固定使用双语对照；如果实际材料只有一种语言，则退化为该语言到另一侧语言的普通单向翻译。正译后再回译只作为未来的质量检查方式，不作为本期交付类型。

### Step 3：选择交付并执行

系统根据材料类型和排版模式动态显示真实格式，并展示任务概览：材料、范围、语言方向、翻译方式、专业条件、排版模式和交付格式。用户点击一次执行按钮后直接进入翻译与交付，不出现第二个人工确认节点。

## 4. 排版与交付规则

### 4.1 交付矩阵

| 材料 | 保留原结构交付 | 商务简洁重排交付 | 不展示 |
|---|---|---|---|
| 单个或多个 DOCX | 每个源文件对应一个 DOCX | DOCX、PDF、TXT、飞书云文档 | XLSX |
| 单个或多个 XLSX | 每个源文件对应一个 XLSX | 本期不提供 | DOCX、PDF、TXT、飞书云文档 |
| 可搜索 PDF | PDF、DOCX、TXT、飞书云文档 | PDF、DOCX、TXT、飞书云文档 | XLSX |
| TXT/Markdown | TXT、DOCX、PDF、飞书云文档 | DOCX、PDF、TXT、飞书云文档 | XLSX |
| 飞书 Docx/Wiki | 飞书云文档、DOCX、PDF、TXT | 飞书云文档、DOCX、PDF、TXT | XLSX |
| 混合材料 | DOCX、PDF、TXT、飞书云文档 | DOCX、PDF、TXT、飞书云文档 | XLSX |

结果卡作为执行摘要自动发送，不作为替代交付文件的假格式。飞书 Docx/Wiki 本期保留标题、段落和列表等可读取结构，但不承诺复制原文档主题、页面设置或复杂嵌入对象。飞书 Sheets 在本期不承诺保留工作簿能力；选中时返回明确的不支持说明和改用本地 XLSX 的恢复路径。

### 4.2 DOCX

- 复制源文档后按段落和表格单元格回填译文。
- 保留段落样式、标题层级、列表、表格、主要字体样式、页眉和页脚。
- 仅译文模式替换文字；双语模式在同一结构节点中保留原文并追加译文。
- 译文长度变化可能造成分页变化，因此产品承诺“保持结构和主要样式”，不承诺像素级锁版。
- 混合行内样式、复杂域、修订记录、文本框或嵌入对象无法可靠保留时，预检返回警告；影响正文完整性时停止任务。

### 4.3 XLSX

- 复制源工作簿，使用 `data_only=False` 读取和保存。
- 只翻译字符串单元格；不修改公式、数字、日期、布尔值和空单元格。
- 保留工作表名称、公式、合并单元格、列宽、行高、冻结窗格、打印设置和基本样式。
- 仅译文模式替换文本单元格；双语模式在同一单元格中以换行保留原文和译文，并保持 `wrap_text`。
- 多个 XLSX 源文件分别生成对应译文工作簿，不合并成伪造的新分析表。
- 检测到宏、外部链接、数据透视表或无法可靠保留的高级对象时停止任务并说明恢复方式。

### 4.4 PDF 和文本

- 可搜索 PDF 按页提取文本并保留页级来源信息，再生成结构化译文 PDF、DOCX、TXT 或飞书云文档。
- PDF 本期不承诺原坐标回填或像素级锁版。
- TXT/Markdown 按标题、段落、列表和表格块翻译并生成所选格式。
- 密码 PDF、扫描 PDF、全空页面或部分页面提取失败都不得静默跳过。

## 5. 系统架构

### 5.1 组件边界

1. 工作台层：现有 `assistant_attachments.py` 负责三步交互、字段展示、顺序校验和材料类型驱动的格式选择。
2. 路由层：现有 `assistant_workbench.py` 负责把已验证的翻译参数放入可信 `start_task` 事件；当 `operation=translate` 时启动专用翻译任务并停止默认单次 LLM 路径，其他研究和文件处理任务保持现状。
3. 任务执行层：新增有界异步翻译执行器。提交卡立即显示“已提交”，执行器在后台解析材料、分批翻译、渲染和校验，完成后向原飞书会话发送结果；任务失败时发送明确错误与恢复路径。
4. 翻译引擎：新增专用 Office translation engine，负责预检、结构提取、翻译单元、模型路由、批处理和完整性校验。
5. 渲染层：按 DOCX、XLSX、PDF 和文本分别回填或重排，不让 LLM 修改二进制文档结构。
6. 交付层：复用现有 Office 交付和飞书卡片能力，把真实文件或飞书云文档发送到原会话并关联结果卡归档。
7. 追溯层：翻译任务启动时先保存 `queued` 运行记录，随后原子更新为 `running`、`completed` 或 `failed`，并把交付文件和重新生成关系附加到现有卡片归档。

专用执行器是翻译正确性的必要边界：Qwen-MT 是单轮翻译模型，全文件必须拆成多次有界调用；不得把完整文件塞入现有的一次普通 LLM 请求，也不得让普通聊天模型伪造格式化译文。进程重启时，仍处于 `queued` 或 `running` 的记录会标记为可重试失败，不自动重复计费调用。

MCP 不是本期内部架构的必要条件。翻译引擎先作为可测试的本地服务模块实现；如果后续 DC-Agent、桌面端和其他 Agent 都需要复用，再增加薄 MCP 适配层，一次提交完整翻译任务，不按段落或单元格产生大量 MCP 调用。

### 5.2 中间结构

每份材料解析为带稳定位置 ID 的翻译清单。每个翻译单元至少包含：

```json
{
  "id": "sheet:报价明细!B12",
  "source_file": "报价.xlsx",
  "kind": "xlsx_cell",
  "location": "报价明细!B12",
  "source_text": "交付周期",
  "detected_language": "zh",
  "target_language": "en",
  "style_ref": "cell-style-7"
}
```

DOCX 使用段落、表格单元格、页眉和页脚位置；PDF 使用页码和块序号；文本使用块序号。翻译结果必须按 ID 一一对应，渲染器只接受通过完整性校验的映射。

### 5.3 模型路由

AIHubMix 已提供 `qwen-mt-plus` 和 `qwen-mt-turbo`。前台显示质量档位，不显示供应商模型名：

| 用户选择 | 后台模型 |
|---|---|
| 快速翻译 | `aihubmix/qwen-mt-turbo` |
| 专业翻译 | `aihubmix/qwen-mt-plus` |
| 智能选择：普通、忠实、单向、无专业条件 | `aihubmix/qwen-mt-turbo` |
| 智能选择：专业润色、行业、术语、翻译记忆或双向互译 | `aihubmix/qwen-mt-plus` |

显式选择专业翻译，或任务因术语、行业、翻译记忆、双向互译而升级到 Plus 时，不静默降级到 Turbo。Plus 不可用时返回可恢复错误。快速翻译只使用 Turbo。

实现前必须以集成测试确认 AIHubMix 会把以下非标准 OpenAI 参数原样转发给 Qwen-MT：

- `source_lang`；
- `target_lang`；
- `terms`；
- `tm_list`；
- `domains`。

如果代理不支持这些参数，服务端返回“专业翻译参数当前不可用”，而不是悄悄改用普通聊天提示词。每次请求按自然段落或完整单元格批量分组；单批源文本最多 8,000 个 Unicode 字符，给语言设置、术语和翻译记忆预留上下文空间。单个翻译单元超过该限制时按完整句子切分，并在渲染前重新合并。

### 5.4 双向互译

双向互译由程序编排，不要求一次模型请求同时翻两个方向：

1. 对每个翻译单元识别它属于语言对中的哪一侧；
2. 将同方向单元批量分组；
3. 以明确的 `source_lang` 和 `target_lang` 调用 Qwen-MT；
4. 将译文按稳定 ID 合并回原清单；
5. 强制使用双语对照渲染。

检测到第三种语言、无法识别语言或同一单元严重混合时，停止该任务并列出位置和恢复方式，不默默保留原文。

语言方向识别先使用文字脚本的确定性快速判断；无法仅靠文字脚本区分的语言对，例如英语和西班牙语，使用现有低成本通用模型 `aihubmix/qwen3.6-flash` 做只允许返回语言对两侧或 `unknown` 的结构化分类。分类仍为 `unknown`，或者同一单元两侧语言占比都显著时，按语言识别失败处理。Qwen-MT 调用始终使用分类后明确的源语言和目标语言，不让翻译模型自行决定双向方向。

## 6. 输入预检与错误恢复

### 6.1 通用限制

- 沿用现有单文件 80 MB、最多 10 项资料和总计 200 MB 限制。
- 单次任务最多处理 500,000 个 Unicode 字符或 20,000 个非空翻译单元，以先达到的限制为准；达到上限时提示按页、章节或工作表缩小范围。
- URL 只接受 HTTPS 直接文件地址；限制重定向、下载大小和超时，并拒绝本机、环回、链路本地和云元数据地址。
- 文件扩展名、MIME 和文件签名不一致时拒绝处理。

### 6.2 明确错误

| 情况 | 系统行为 | 恢复路径 |
|---|---|---|
| 超大文件或单元过多 | 不进入模型调用 | 缩小范围或拆分文件 |
| 密码 PDF | 不尝试猜测密码 | 用户解除密码后重新上传 |
| 扫描 PDF | 不生成空译文 | 转到后续图片/扫描件翻译能力，或先 OCR |
| 部分页提取失败 | 整个任务不交付 | 列出页码，用户修复或排除对应页 |
| 不支持格式 | 不进入模型调用 | 转换为 DOCX、XLSX、TXT、MD 或可搜索 PDF |
| 语言识别失败 | 不静默猜测 | 用户手动指定源语言或语言对 |
| 模型输出缺少 ID | 不生成文件 | 自动重试一次；再次失败则提示重试 |
| 专业参数未被代理支持 | 不降级普通提示词 | 修复 AIHubMix provider 参数转发 |
| 飞书文档无权限 | 不声称已读取 | 把机器人加入协作者后重试 |
| 文件生成失败 | 保留翻译运行记录，不发送残缺文件 | 使用相同任务 ID 重试渲染 |

## 7. 质量校验

在生成文件前执行确定性校验：

- 翻译单元 ID 数量与集合完全一致；
- 不允许空译文，除非源文本仅包含空白或不可翻译符号；
- 公式、数字、日期、URL、邮箱和品牌保护词不得被误改；
- 术语表中的强制术语必须命中；
- 单向翻译结果必须符合目标语言；
- 双向翻译每个单元必须符合其对应方向；
- 译文长度异常、重复输出或明显截断触发一次自动重试；
- DOCX/XLSX 输出重新打开验证，PDF 输出重新读取并确认至少一页和非空文本；
- 任何校验失败都不得交付貌似成功的文件。

## 8. 追溯与重新生成

每次执行生成一个运行 ID，并保存：

- 工作台 token 和会话任务 ID；
- 原材料文件名、来源类型、哈希或云文档 URL；
- 翻译范围；
- 源语言、目标语言或双向语言对；
- 翻译方式、专业领域、术语表和翻译记忆摘要；
- 用户选择的质量档和实际模型；
- 排版模式和交付格式；
- 警告、错误、重试次数；
- 交付文件路径或飞书文档 URL；
- 父运行 ID 和重新生成序号。

运行清单写入运行时输出目录，不进入 git。交付文件继续附加到现有结果卡归档。用户补充要求后重新生成时，新的运行记录引用上一次运行 ID，但不覆盖上一版文件。

## 9. 自动化验证

### 9.1 工作台和 API

- “处理文件”保持材料 → 任务 → 交付的三步顺序和白色背景。
- 没有材料不能选择或提交翻译任务。
- 单向翻译必须选择目标语言。
- 双向互译必须选择语言对并自动使用双语对照。
- 根据材料类型只显示真实格式。
- 保存后直接执行，不出现第二个人工确认。
- 不改变“查资料/分析”的字段和执行语义。

### 9.2 翻译引擎

- DOCX 标题、段落、列表、表格、页眉和页脚结构保持。
- XLSX 工作表、公式、数值、样式、合并单元格、列宽和行高保持，文本单元格被替换。
- 双语模式在 DOCX 和 XLSX 中保留原文和译文。
- PDF 密码、扫描、部分页失败和空文本得到明确错误。
- 语言识别、术语命中、缺少 ID、异常截断和不支持格式得到自动化证据。
- 模型路由符合 Turbo/Plus 规则，专业模式不静默降级。
- AIHubMix `translation_options` 参数经过模拟集成测试。

### 9.3 交付与追溯

- Word、Excel、PDF、TXT 都是真实可打开文件。
- 飞书云文档确实调用 OpenAPI 创建并写入内容。
- 结果卡只引用实际生成的文件。
- 运行清单关联原材料、语言、方式、模型、交付物和重新生成关系。

## 10. 发布边界

实现完成后运行相关定向测试、Ruff 和 `scripts/agent-check.sh --profile targeted`，逐项处理输出。当前脏工作树中的既有修改和未跟踪文件不得清理、覆盖或纳入无关变更。本任务只准备发布所需代码和验证结果；未经用户再次明确确认，不提交、不推送、不发布、不修改生产配置。
