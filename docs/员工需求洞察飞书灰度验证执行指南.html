员工需求洞察飞书灰度验证执行指南

1. 验证目标

本指南用于验证“员工需求洞察闭环系统”的飞书私聊触达链路，目标是确认系统可以在不触达真实员工、不扩大打扰范围的前提下，完成一次工程级灰度验证。

验证范围只覆盖：

  • • 试点员工画像进入 active 状态。
  • • 后台生成每日触达计划。
  • • 后台执行 dry-run 预演。
  • • 真实发送闸门可以阻止未授权请求。
  • • 授权后可以向指定测试 open_id 发送飞书私聊。
  • • 首轮触达优先使用 employee_insight_welcome 小白入口卡片。
  • • 员工回复后 AstrBot 插件可以记录会话、事件和画像状态。
  • • 一键验证可以模拟员工回复和暂停退出，检查事件是否落库。
  • • 后台可以自动计算发送率、打开率、表单打开率、提交率和异常率。
  • • 指标不达标时后台必须给出回滚原因和修复动作。
  • • 发送、失败、跳过、回复都可以进入审计。

本次验证不覆盖：

  • • 全员触达。
  • • 批量导入真实员工名单。
  • • 未经审批的自学习发布。
  • • 未经 Obsidian 审批的 router、skill、知识库变更。

2. 参与角色

角色人数责任
管理员1创建测试群、配置飞书应用、控制审批 token
开发1配置回调、检查日志、执行接口验证
产品或业务代表1验证文案是否像“同事陪跑”，不是问卷
测试员工1-3使用测试 open_id 模拟员工回复

测试员工必须使用内部测试账号或明确授权的内部成员，不使用正式中台员工做首轮验证。

3. 飞书应用配置清单

3.1 应用类型

配置项建议值
应用类型企业自建应用或机器人
使用范围仅测试群或指定测试成员
触达方式open_id 私聊
回调方式事件订阅 HTTP 回调

3.2 权限申请

权限用途是否必需
im:message 或同等消息发送权限给测试 open_id 发送私聊必需
im:message:send_as_bot以机器人身份发送消息必需
im:message.receive_v1接收员工回复事件必需
contact:user.id:readonly根据测试成员确认 open_id建议
im:chat如果需要创建测试群可选

如果飞书后台权限名称与上表略有差异，以当前飞书开放平台后台展示为准，但必须满足两个能力：机器人可向指定 open_id 发消息，系统可接收测试员工回复。

3.3 回调地址

回调地址应指向当前 AstrBot/Lark 事件入口，而不是员工洞察后台看板接口。

建议格式：

https://<你的公网回调域名>/<现有 AstrBot 飞书事件入口>

配置原则：

  • • 不新增绕过 feishu_channel_control 的临时入口。
  • • 不把 dashboard API 暴露给飞书事件订阅。
  • • 回调地址必须能收到飞书 challenge 校验和消息事件。
  • • 回调日志中必须能看到测试 open_id、message id 和事件类型。

4. 系统配置清单

4.1 飞书凭证

飞书 app_id 和 app_secret 继续走仓库既有统一入口：

data/feishu_whitelist.yaml

或既有兼容入口：

nas_sync/config.yaml

配置要求：

  • • 不把 app_secret 写进文档、截图或 issue。
  • • 不把测试 open_id 与真实姓名批量提交到 git。
  • • 凭证加载仍由 dc_engines.feishu_hub 统一管理。

4.2 员工洞察真实发送配置

后台真实发送必须显式开启：

employee_insight:
  real_sender_enabled: true
  real_send_approval_token: "<只给管理员和开发知道的一次性审批 token>"

安全约束：

  • • real_sender_enabled 默认为关闭。
  • • 没有 real_send_approval_token 时真实发送必须失败。
  • • 请求里的 approval_token 必须与配置一致。
  • • approved 必须为 true。
  • • 发送对象必须来自 active 试点画像。

5. 验证前准备

5.1 创建飞书测试群

建议创建一个只包含管理员、开发、产品或业务代表、测试员工的群。

群名建议：

员工需求洞察灰度验证群

用途：

  • • 统一记录验证节奏。
  • • 不直接在群里触发员工洞察私聊。
  • • 避免把验证消息误发到真实业务群。

5.2 准备测试员工画像

推荐方式是不手动查 open_id，而是让测试账号直接私聊小助手：

加入灰度验证

系统会自动读取飞书私聊事件里的 sender id，并登记为测试画像：

  • • pilot_status=active
  • • metadata.verification_scope=true
  • • metadata.self_registered=true

这样管理员不需要知道 open_id，也不需要把测试成员名单写入配置。

如需手动兜底，也可以通过后台接口或后台页面新增测试画像：

{
  "employee_id": "ou_xxx_test",
  "employee_hash": "hash_xxx_test",
  "display_name": "测试员工A",
  "department_id": "middle_office",
  "role": "测试",
  "pilot_status": "active"
}

手动方式要求：

  • • employee_id 使用飞书 open_id。
  • • pilot_status 必须为 active。
  • • 首轮只准备 1 个测试账号。
  • • 第二轮最多扩到 3 个测试账号。

5.3 准备测试消息

推荐首条消息：

今天想试一个真实工作任务吗？你可以直接把要做的事发给我，也可以回复：查资料 / 写通知 / 整理文件 / 生成汇报 / 不知道怎么用。

文案原则：

  • • 不要求员工填问卷。
  • • 不问“你有什么需求”这种抽象问题。
  • • 只邀请员工拿一个真实小任务试用。
  • • 明确支持暂停和退出。

首轮正式触达优先发送飞书 interactive card，而不是纯文本。卡片类型为：

employee_insight_welcome

卡片必须提供四个新手入口：

  • • 写通知
  • • 整理资料
  • • 生成汇报
  • • 我不知道怎么用

如果飞书卡片发送失败，系统才回退为纯文本触达。

6. 验证步骤

Step 1：检查触达计划

请求：

GET /api/employee-insight/outreach-plan?limit=10

通过标准：

  • • 测试员工出现在 eligible。
  • • 非 active 员工出现在 skipped。
  • • 当天已触达员工会被标记为 already_contacted_today。
  • • 连续未回复达到阈值后会进入 cooldown_after_unanswered。

Step 2：执行 dry-run 预演

请求：

POST /api/employee-insight/outreach-dispatch
Content-Type: application/json

{
  "dry_run": true,
  "approved": false,
  "limit": 10
}

通过标准：

  • • 返回 mode=dry_run。
  • • sent 为空。
  • • 不调用飞书发送 API。
  • • 审计中出现 outreach_dry_run。

Step 3：验证未授权真实发送会被拒绝

请求：

POST /api/employee-insight/outreach-dispatch
Content-Type: application/json

{
  "dry_run": false,
  "approved": true,
  "approval_token": "wrong-token",
  "limit": 1
}

通过标准：

  • • 返回错误。
  • • 错误信息包含 approval_token。
  • • 飞书端收不到消息。
  • • 员工画像的 last_outreach_at 不更新。

Step 4：执行一次授权真实发送

请求：

POST /api/employee-insight/outreach-dispatch
Content-Type: application/json

{
  "dry_run": false,
  "approved": true,
  "approval_token": "<真实审批 token>",
  "limit": 1,
  "message_text": "今天想试一个真实工作任务吗？你可以直接把要做的事发给我，也可以回复：查资料 / 写通知 / 整理文件 / 生成汇报 / 不知道怎么用。"
}

通过标准：

  • • 返回 mode=send。
  • • sent 中包含测试员工。
  • • 返回 provider_message_id。
  • • 飞书测试账号收到私聊。
  • • 系统创建 daily_outreach session。
  • • 员工画像的 last_outreach_at 更新。
  • • unanswered_outreach_count 加 1。
  • • 审计中出现 outreach_sent。

Step 5：模拟员工回复

测试员工在飞书私聊中回复：

我想让你帮我写一段给项目组的培训通知，但不知道怎么描述。

通过标准：

  • • AstrBot 插件识别为 lark_dm。
  • • 创建或更新 employee insight session。
  • • 写入 employee_replied 和 task_started 事件。
  • • 员工画像的 unanswered_outreach_count 归零。
  • • 系统回复应继续陪跑任务，而不是要求员工填写问卷。

Step 6：验证退出机制

测试员工回复：

暂停

通过标准：

  • • session 状态进入 muted。
  • • 写入 opt_out 事件。
  • • 后续触达计划中该员工不再进入 eligible。

Step 7：执行一键灰度验证

后台页面可以直接点击“自动检查”或“授权发送 1 人”。也可以调用接口：

POST /api/employee-insight/verification/run
Content-Type: application/json

{
  "approval_token": "<真实审批 token>",
  "send_one": false
}

如果只想做安全检查，send_one=false。如果要给 1 个测试账号真实发一条消息，改为：

{
  "approval_token": "<真实审批 token>",
  "send_one": true
}

通过标准：

  • • dry_run_no_send=true
  • • wrong_token_blocked=true
  • • simulated_reply_recorded=true
  • • simulated_pause_recorded=true
  • • 如果 send_one=true，只允许发送给 metadata.verification_scope=true 的 1 个测试画像。

Step 8：查看灰度指标报告

后台页面会展示灰度指标验收，也可以调用接口：

GET /api/employee-insight/verification/report

报告包含：

  • • sent_rate：发送率
  • • open_rate：打开率
  • • form_open_rate：表单打开率
  • • submit_rate：提交率
  • • anomaly_rate：异常率
  • • go_no_go：是否允许扩面
  • • rollback：是否需要回滚、原因和动作

7. Go/No-Go 判定

满足以下全部条件，才允许进入 3-10 人灰度。

7.1 链路门槛

序号条件标准
1dry-run 不触发真实发送100% 通过
2错误 token 不能发送100% 通过
3授权发送只触达测试 open_id100% 通过
4发送成功有 provider message id100% 通过
5员工回复可进入结构化事件100% 通过
6暂停/退出机制有效100% 通过
7发送失败不更新触达时间100% 通过
8审计记录完整100% 通过
9小白入口卡片可生成100% 通过
10模拟员工回复可落库100% 通过
11模拟暂停退出可落库100% 通过

7.2 指标门槛

指标标准
发送率 sent_rate≥95%
打开率 open_rate≥80%
表单打开率 form_open_rate≥95%
提交率 submit_rate≥90%
异常率 anomaly_rate≤5%

任一链路条件或指标条件不满足，判定为 No-Go，必须修复后重新验证。

7.3 回滚条件

出现以下任一情况，必须停止扩面：

  • • 发送率低于 95%。
  • • 打开率低于 80%。
  • • 表单打开率低于 95%。
  • • 提交率低于 90%。
  • • 异常率高于 5%。
  • • 出现发送失败、权限错误、回调丢失、按钮无响应或员工无法退出。

回滚动作：

  • • 停止扩大灰度范围。
  • • 保留当前样本、事件日志和审计记录。
  • • 修复权限、卡片、回调、表单或陪跑话术。
  • • 重新执行一键灰度验证。
  • • 指标恢复达标前，不进入下一批员工。

9. 下一阶段扩面规则

9.1 1 人测试通过后

可以扩到 3 人，但必须保持：

  • • 同一部门优先。
  • • 每人每天最多 1 次触达。
  • • 任意 1 人回复暂停，立即尊重退出。
  • • 每天复盘一次卡点。

9.1.1 每日自动触达任务

灰度验证通过后，可以开启插件每日自动触达任务：

daily_outreach_enabled: true
daily_outreach_cron: "0 10 * * *"
daily_outreach_timezone: "Asia/Shanghai"
daily_outreach_real_send_enabled: false

默认必须保持 daily_outreach_real_send_enabled=false，先观察 dry-run 结果。确认 1 人测试账号完全通过后，再由管理员配置审批字段：

daily_outreach_real_send_enabled: true
daily_outreach_approved: true
daily_outreach_approval_token: "<审批 token>"

每日任务仍然遵守试点画像、频率限制、冷却期和暂停退出规则。

9.2 3 人测试通过后

可以进入 10 人试点，但必须新增：

  • • 管理员看板日汇总。
  • • 候选需求 Obsidian 审批流。
  • • Hermes 深挖候选队列。
  • • router/skill/知识库发布前测试。

9.3 不允许直接进入全员

即使 10 人试点通过，也不建议直接全员触达。下一步应该按部门、岗位、任务场景逐步扩面。

10. 管理员检查清单

  • • [ ] 飞书应用权限已最小化授权。
  • • [ ] 回调地址指向现有 AstrBot 飞书事件入口。
  • • [ ] 测试群已创建，且不包含正式被验证员工。
  • • [ ] 测试 open_id 已确认。
  • • [ ] real_sender_enabled 已按验证窗口临时开启。
  • • [ ] real_send_approval_token 已配置，且验证后会轮换。
  • • [ ] dry-run 已通过。
  • • [ ] 错误 token 拦截已通过。
  • • [ ] 真实发送只发送给 1 个测试账号。
  • • [ ] 发送结果、员工回复、暂停退出、失败路径均有审计。
  • • [ ] 验证结束后关闭真实发送开关或轮换审批 token。

11. 结论

灰度验证的核心不是“能不能发出去”，而是确认系统是否具备可控触达、可撤回、可审计、可复盘、可逐步扩面的能力。

只有当发送链路、回复链路、退出链路、审计链路全部稳定后，才应该进入真实员工小范围试点。
