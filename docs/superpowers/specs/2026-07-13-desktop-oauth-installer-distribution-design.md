# 巅池桌面助手 OAuth、安装分发与宠物接入设计

## 目标

让公司员工从已部署在 Vercel 的公司主页进入统一的桌面端使用流程：先完成飞书 OAuth，再通过公司员工权限名单校验身份；已安装时直接唤起“巅池桌面助手”，未安装时进入尽可能少操作的安装流程。外部账号、待审核账号和停用账号不得获得安装授权或桌面端会话。

桌面端继续使用官方飞书 Messenger 作为“消息”主界面，并保留本地宠物渲染。该设计不复制飞书客户端代码，也不把完整飞书页面重新嵌入公司工作台。

## 已确认的产品规则

- 飞书 OAuth 只负责证明登录者是谁，公司员工库负责决定是否允许使用。
- 只有 `status=active` 的内部员工可以进入桌面端检测、下载安装和授权流程。
- `pending`、`disabled`、租户不匹配或名单中不存在的账号一律拒绝，页面明确显示“该账号不是公司内部员工或尚未获得授权”。
- 公司组织身份与系统权限分开保存。杨国民是唯一 `boss`；蔡挺的组织身份是 AI 应用部门负责人，使用 `relation_type=manager`，系统权限为最高级 `role=admin`。
- Windows 是主要平台，采用普通员工可以完成的每用户安装方式；macOS 同时提供独立安装包。
- 安装包使用 Vercel Blob 分发，采用不可变版本路径；Vercel API 只返回当前推荐版本的清单。
- 正常网页无法静默执行本地安装程序。“自动安装”定义为：授权通过后自动检测、自动开始下载、安装器自动配置并启动；Windows 第一次仍需要员工点击一次浏览器下载项或系统确认。

## 当前状态与需要修正的问题

### 已有能力

- `dianchi` 官网已经具备飞书 OAuth、登录 cookie、员工状态判断和 `dianchi://` 桌面协议入口。
- `dianchi-desktop` 已经具备官方飞书 Messenger 嵌入、持久化飞书登录数据、公司品牌名称和协议注册基础。
- DC-Agent 已经具备 `employees.db`、飞书身份映射和 `/api/pet/bind-desktop` 等宠物身份接口。
- Vercel 项目已有 Upstash Redis REST 抽象，可作为员工授权镜像和一次性授权码存储。

### 当前缺口

- Vercel 函数仍尝试按本地路径打开 SQLite。云端函数无法读取 `/Users/dianchi/DC-Agent/data/employees.db`，也不能把函数实例的临时文件当作公司权限数据库。
- OAuth 遇到陌生账号时会自动创建 `pending` 身份。安装入口需要改为默认拒绝，不能把自动建档等同于员工授权。
- 当前 `dianchi://open?session=...` 把完整签名会话放进自定义协议 URL。会话可能进入浏览器历史、系统日志或被其他协议处理程序看到。
- 普通网页不能可靠枚举本机软件，必须通过自定义协议唤起和服务端心跳组合判断。
- 当前员工数据库运行在 DC-Agent 本机，NAS 只挂载了知识库共享；不能把尚未存在于 NAS 的 SQLite 误称为 NAS 实时员工库。

## 现有 Vercel 主页审查与增量改造边界

2026 年 7 月 13 日核对线上 `https://dianchi2026.vercel.app` 后确认，现有产品方向与本设计一致，不需要重做官网：

- 线上主页已经有“员工飞书登录”入口，`/api/auth/feishu/start` 能正确跳转飞书 OAuth。
- 线上 `/api/me` 已能识别基础登录态，但仍是旧响应，只返回 `logged_in`、`user` 和 `activated`。
- 线上尚未发布 `/desktop.html`、`/agent.html` 和 `/api/desktop/open`，这些路径当前返回 404。
- 本地 `dianchi` 工作区已经把主页文案改为“飞书登录激活桌面端”，并已添加 `desktop.html`、员工身份分层和 `dianchi://` 唤起草案；这些现有改动应继续保留。
- 本地草案仍使用 Vercel 无法访问的 SQLite，并通过 `dianchi://open?session=...` 传递完整会话；只替换这两处实现，不推翻已有页面和路由。

因此实施采用局部修改，文件边界如下：

| 现有区域 | 处理方式 |
|---|---|
| `index.html` | 保留全部官网布局、视频、品牌内容和视觉样式；只校正员工入口链接、登录后文案和目标页 |
| `api/auth/feishu/start.py` | 保留现有 OAuth 发起、state 和安全 `next` 路径逻辑 |
| `api/auth/feishu/callback.py` | 保留飞书换 token 和用户信息获取；只把 SQLite 身份解析替换为 Upstash 授权镜像，并为拒绝状态返回明确页面 |
| `api/me.py` | 在现有接口上稳定补充 `allowed`、`auth_status`、`employee` 和 `identity`，不另建重复登录接口 |
| `desktop.html` | 复用本地已有启动页，局部增加协议探测、未安装下载、失败重试和授权状态，不把安装逻辑塞回官网首页 |
| `api/desktop/open.py` | 保留入口名称和鉴权顺序，把完整 session 深链替换成一次性授权码 |
| `api/_kv.py` | 复用现有 Upstash REST 配置，增加授权快照和短时码所需的严格操作；生产授权路径禁止内存兜底 |
| `/api/activate` 和钱包/宠物接口 | 保留现有幂等激活逻辑，只在员工授权通过后调用 |
| `workspace.html`、官网业务展示和视频模块 | 不在本项目范围内修改 |

实施时必须保护 `dianchi` 当前未提交的本地改动，先为相关文件建立基线并仅编辑上述授权与启动边界，不能用线上旧文件覆盖本地新版主页。

## 系统边界

| 单元 | 责任 | 主要依赖 |
|---|---|---|
| Vercel 公司主页 `dianchi` | 飞书 OAuth、员工授权镜像查询、安装状态页、版本清单、一次性桌面授权码 | 飞书开放平台、Upstash Redis、Vercel Blob |
| DC-Agent | 公司员工目录真源、授权名单投影与同步、宠物身份和事件服务 | `employees.db`、飞书通讯录、公司内网 |
| 巅池桌面助手 `dianchi-desktop` | 协议注册、官方飞书消息界面、本地宠物渲染、安装后授权交换 | Vercel API、飞书网页、内网 DC-Agent API |
| NAS `192.168.1.35` | 内网知识库、宠物资源或备份等公司数据服务 | 公司局域网 |

DC-Agent 本机的员工目录是现阶段员工授权真源。NAS 可以保存加密备份，但不直接通过 SMB 运行 SQLite，避免网络文件锁和断线造成数据库损坏。

## 员工授权镜像

### 数据投影

DC-Agent 从 `employee_accounts` 和 `employee_identities` 生成最小授权快照。每条记录只包含：

- `employee_id`
- `tenant_key`
- `feishu_open_id`
- `feishu_union_id`
- `feishu_user_id`
- `display_name`
- `department`
- `title`
- `relation_type`
- `role`
- `status`
- `updated_at`

授权优先使用 `tenant_key + feishu_user_id` 或 `tenant_key + feishu_union_id`，并保留应用范围内的 `open_id` 作为兼容索引。姓名、邮箱和部门名称只能展示，不能作为授权主键。

### 同步方式

DC-Agent 定时生成完整快照，并使用独立的 HMAC 同步密钥调用 Vercel 内部同步接口。Vercel 校验签名、时间戳和快照版本后，原子替换 Upstash 中的单一授权快照。当前规模只有几十人，完整快照比增量同步更简单，也不会遗留已删除员工。

- 员工目录变更后立即同步。
- 定时任务每 5 分钟补偿同步一次。
- 快照包含 `version`、`generated_at`、记录数量和内容摘要。
- 同版本重复提交幂等处理；旧版本拒绝覆盖新版本。
- Vercel 未配置持久化 KV 时，生产环境必须拒绝授权，不允许降级到进程内内存名单。
- 快照超过 24 小时仍未更新时，安装授权失败关闭；已安装客户端的短期离线使用由本地有效会话策略处理。

### 身份与权限分层

组织层和系统层不得互相推导：

| 人员 | 组织身份 | 系统权限 |
|---|---|---|
| 杨国民 | `relation_type=boss`，总经办，杨总 | 按公司权限模型分配，不因老板身份自动成为系统超级管理员 |
| 蔡挺 | `relation_type=manager`，AI 应用部，AI 应用部门负责人 | `role=admin`，系统最高权限 |

安装资格只依据同一公司租户、身份记录存在且 `status=active`。`boss`、`manager`、`employee` 不影响是否能安装，`role=admin` 也不能绕过停用状态。

## OAuth 与安装数据流

### 1. 飞书登录与公司校验

1. 员工点击公司主页的“员工登录桌面端”。
2. Vercel 发起飞书 OAuth，并使用带签名、短时有效的 state 防止回调伪造。
3. 回调取得 `tenant_key`、`open_id`、`union_id` 和 `user_id`。
4. 先校验公司 `tenant_key`，再查询 Upstash 中的员工授权快照。
5. 只有匹配记录且 `status=active` 时才创建公司网页登录态。
6. 其他账号直接返回拒绝页，不返回安装包入口、不创建桌面授权码、不调用宠物绑定。

### 2. 检测桌面端

1. 授权页向 Vercel 创建一个短时 `probe_id`。
2. 页面尝试打开 `dianchi://probe?probe_id=...`。
3. 已安装的桌面端收到协议后向 Vercel 上报该 `probe_id` 心跳。
4. 页面在约 3 秒内轮询检测结果。收到心跳则进入授权唤起；未收到则进入安装流程。

该检测只证明协议处理程序成功响应，不声称网页扫描了本机安装目录。

### 3. 首次安装

1. 页面根据操作系统和 CPU 架构请求 `/api/desktop/latest`。
2. API 返回版本、平台、架构、Blob URL、文件大小和 SHA-256。
3. 页面自动开始一次下载，并保留醒目的“重新下载”按钮处理浏览器拦截。
4. Windows 使用每用户安装器写入 `%LOCALAPPDATA%`，注册 `dianchi://`，创建开始菜单入口，完成后自动启动应用；不依赖管理员权限。
5. macOS 使用签名应用包或 DMG，应用名称和 Dock 名称均为“巅池桌面助手”，图标使用公司 Logo。
6. 应用首次启动后打开同一 Vercel 授权页。浏览器已有飞书登录态，因此不会要求员工再次扫码，除非网页登录已过期。

### 4. 桌面授权交换

1. Vercel 为已通过员工校验的登录态生成 60 秒有效、只能使用一次的随机授权码。
2. 页面通过 `dianchi://authorize?code=...` 唤起桌面端。
3. 桌面端把授权码发送到 `/api/desktop/exchange`，并附带本机生成的安装实例 ID。
4. 服务端原子消费授权码，返回桌面会话；同一码第二次使用、过期使用或员工已停用时均失败。
5. 自定义协议中不再携带完整网页登录 cookie、飞书 access token 或宠物绑定密钥。

桌面会话只绑定员工身份和安装实例，不自动取得管理员操作权限。敏感管理 API 仍按服务器端 `role` 和权限记录单独鉴权。

桌面端取得 8 小时访问令牌和最长 30 天的安装实例刷新凭证。刷新凭证保存在 Windows Credential Manager 或 macOS Keychain，不写入普通配置文件。每次启动和刷新都重新检查员工授权镜像；员工变为 `disabled` 后不再签发访问令牌。飞书 Messenger 自身的登录 cookie 继续由专用 WebEngine profile 管理，不与公司桌面会话混用。

## 安装包与版本发布

Vercel Blob 使用公开、不可变、带版本号的对象路径，例如：

```text
desktop/windows/x64/0.2.0/DianchiDesktopAssistantSetup.exe
desktop/macos/arm64/0.2.0/DianchiDesktopAssistant.dmg
```

安装包中不得包含飞书应用密钥、Vercel KV token、DC-Agent 绑定密钥或员工名单。公开下载本身不等于可使用；桌面端每次首次授权仍必须通过员工校验。

`/api/desktop/latest` 返回受控清单，而不是在网页中硬编码 Blob 地址。发布新版本时先上传不可变文件，再更新清单。回滚只需把推荐版本指回上一份已经验证的文件。

发布流水线在更新清单前下载回读 Blob 并核对 SHA-256。Windows 正式安装器使用公司代码签名证书签名，macOS 应用完成 Developer ID 签名和 notarization；没有签名的构建只允许进入内部灰度清单。后续自动更新由桌面端在执行前同时校验清单摘要和平台签名。

## 宠物系统接入

- 宠物窗口、动画和基础资源继续在桌面端本地运行，避免每次动作都依赖网络。
- 飞书员工身份通过一次性桌面授权交换绑定到稳定的 `employee_id`；宠物状态不能只绑定易变化的 OAuth cookie。
- 桌面端在公司内网使用 60 秒有效的绑定凭证调用 DC-Agent 的宠物接口。该凭证由 Vercel 使用独立的 `DESKTOP_BINDING_SECRET` 做 HMAC-SHA256 签名，包含 `employee_id`、`desktop_session_id`、随机 nonce 和过期时间，不包含共享密钥。DC-Agent 校验签名并拒绝 nonce 重放后，复用现有 `/api/pet/bind-desktop` 逻辑，把 `employee_id`、`pet_id` 和 `desktop_session_id` 关联起来。
- 服务端继续保存金币、已解锁角色、试用状态和业务事件；客户端只缓存展示所需数据。
- NAS/DC-Agent 暂时不可达时，飞书消息界面仍可使用，宠物展示最后一次有效缓存并标记离线；涉及金币、购买、试用和身份变更的写操作禁止离线伪造。

## 错误处理

| 场景 | 用户表现 | 系统行为 |
|---|---|---|
| 飞书 OAuth 取消或 state 过期 | 提示重新登录 | 不创建公司会话 |
| 非公司租户或名单不存在 | “该账号不是公司内部员工” | 403，隐藏安装和授权入口 |
| `pending` | “账号尚未开通，请联系管理员” | 403，不自动升级状态 |
| `disabled` | “账号已停用” | 403，并拒绝新的桌面会话 |
| 授权快照缺失或过期 | “员工身份服务暂不可用” | 失败关闭并记录告警 |
| 协议未响应 | 自动转入安装页 | 不把未响应直接记录为故障 |
| 浏览器拦截下载 | 展示单一大按钮重新下载 | 保留已完成的飞书登录态 |
| 一次性授权码过期 | 自动重新申请一次 | 不复用旧码，不暴露会话 |
| 安装包摘要不一致 | 阻止安装并提示重新下载 | 记录版本和摘要错误 |
| 宠物服务离线 | 宠物显示离线，消息仍可用 | 禁止服务端状态写入，恢复后重连 |

## 测试与验收

### 自动化测试

- 员工快照测试：完整替换、版本倒退拒绝、HMAC 错误拒绝、缺少持久化 KV 时生产授权拒绝。
- OAuth 测试：公司 `active` 员工通过；外部租户、未知、`pending`、`disabled` 全部拒绝且没有安装入口。
- 身份测试：杨国民是唯一 `boss`；蔡挺是 `manager + admin`，系统权限不会改变组织身份。
- 桌面授权测试：授权码 60 秒过期、只能消费一次、不会出现在返回日志中的长期会话字段。
- 协议检测测试：心跳成功进入授权；超时进入安装；重复 probe 幂等。
- 版本清单测试：平台和架构匹配、版本路径不可变、SHA-256 与构建产物一致。
- 宠物绑定测试：同一员工重装后仍绑定原宠物；其他员工不能接管已有桌面会话；NAS 离线不影响飞书消息页启动。
- 现有 `feishu_desktop_messenger`、`organization_permission_model` 和 `pet_live_system` 契约继续通过。

### 真机验收

1. 一台从未安装过的 Windows 电脑：飞书登录、自动下载、一次点击安装、自动启动、消息页打开、宠物绑定成功。
2. 一台已安装的 Windows 电脑：OAuth 后 3 秒内被协议检测并直接打开，不重复下载。
3. 两台 macOS 电脑：应用名称、Dock 图标、授权持久化和 Messenger 布局正确。
4. 一个名单外飞书账号：只能看到非内部员工提示，无法取得安装授权。
5. 一个 `pending` 测试账号和一个 `disabled` 测试账号：均被准确拒绝。
6. 断开 NAS/DC-Agent：飞书消息仍可打开，宠物进入明确离线状态；网络恢复后自动重连。

## 实施顺序

1. 先修正并测试身份分层：杨国民唯一 `boss`，蔡挺为 `manager + admin`。
2. 为桌面安装授权建立新的最小契约和测试，不修改无关业务模块。
3. 实现 DC-Agent 授权快照生成与签名同步。
4. 把 Vercel OAuth 员工判断从本地 SQLite 改为持久化授权镜像，并完成拒绝页面。
5. 把完整 session 深链改为一次性授权码交换。
6. 完成 Windows 与 macOS 安装产物、协议注册和 Vercel Blob 版本清单。
7. 接入宠物身份断言与离线降级。
8. 先对蔡挺和两台测试电脑灰度，再扩大到 3 至 5 名员工，最后全员开放。

## 非目标

- 不重做现有 Vercel 官网，不改变主页主体布局、视频、作品案例和对外品牌内容。
- 不通过网页静默运行 EXE 或绕过操作系统安全确认。
- 不复制、逆向或重新实现飞书 Messenger。
