「活系统」之宠物系统分支开发全栈方案与落地计划

把飞书小助手、DC-Agent 宠物状态核心、dianchi-desktop 本地客户端和 Codex Pets 风格宠物场景打通，让员工看到的是同一只会响应工作状态的宠物。

日期：2026-06-15 分支：feature/live-pet-system 范围：DC-Agent + dianchi-desktop 目标：同身份、同事件流、同状态机

一、核心结论

可以升级，而且应该按“活系统”做。桌面端宠物不只是一个皮肤，而是飞书小助手的可视化身体；飞书里的 `/pet` 卡片和桌面端看到的必须是同一只宠物。
现有资产位置活系统角色
飞书宠物助手 MVPDC-Agent/data/plugins/feishu_pet_assistant/业务入口、任务闭环、宠物卡片
宠物 SQLiteDC-Agent/data/feishu_pet.db宠物状态和任务事件种子
本地客户端/Users/dianchi/dianchi-desktop桌面壳、登录态、宠物可视化容器
Codex Pets 参考codex-pets.net宠物包、动画状态、场景交互参考

二、目标架构

飞书用户
飞书小助手
Pet Live Core
Pet API
桌面宠物场景

关键原则是：同一身份、同一事件流、同一状态机、双端展示、渐进实时。第一阶段使用短轮询即可，稳定后再升级 SSE 或 WebSocket。

飞书小助手 / 卡片动作 / 任务事件
  -> DC-Agent Pet Live Core
  -> pet_event_outbox + pet state reducer
  -> /api/pet/me 与 /api/pet/events
  -> dianchi-desktop PetRuntime
  -> QWebEngineView 中的 React/Vite 宠物场景

三、数据模型

身份映射：pet_identity_links

字段说明
pet_id宠物全局 ID
feishu_open_id飞书 sender open_id
employee_id员工目录 ID，可后补
desktop_session_id桌面端 dc_feishu_session 绑定

事件流：pet_event_outbox

事件来源宠物状态
assistant_message_received飞书聊天waiting
assistant_thinking_startedRouter / Hermes / Codexworking
assistant_response_sent小助手回复成功success / happy
assistant_response_failed执行失败failed
task_completed任务完成success，增加经验和能量

四、接口契约

当前宠物

GET /api/pet/me

返回宠物档案、状态、任务统计和 last_event_id。

事件增量

GET /api/pet/events?after_id=...

桌面端按游标获取新事件。

桌面心跳

POST /api/pet/heartbeat

记录桌面在线、版本和最后消费游标。

宠物动作

POST /api/pet/actions

第一版支持 feed，后续支持换装和场景动作。

七、P0 验收标准

  1. 飞书 open_id、桌面 session、pet_id 能稳定绑定。
  2. /pet 卡片和桌面宠物展示同一只宠物。
  3. 飞书消息或任务事件能写入 pet_event_outbox。
  4. 桌面端能通过 API 拉取当前宠物和增量事件。
  5. 宠物状态由服务端 reducer 统一生成。
  6. 桌面端重启后不丢失登录态和宠物游标。
  7. 所有新增功能默认可配置关闭。

八、风险处理

风险处理
身份错绑所有 API 基于服务端 session 解析身份，不信任前端传 user_id。
桌面端离线本地缓存最后状态，恢复后用 after_id 补事件。
飞书事件太多reducer 节流，低价值消息只更新活跃时间。
动画过早复杂第一版只支持 spritesheet manifest，不做编辑器。
玩具化每个动画状态必须绑定真实业务事件。
推荐顺序：先身份绑定，再事件 outbox，再 reducer，再桌面 API，最后做 Codex Pets 风格渲染。

九、最终定义

飞书小助手 = 它的嘴
DC-Agent pet_live = 它的大脑和记忆
dianchi-desktop = 它的身体
Codex Pets 风格场景 = 它被员工看见的生活空间

这条分支完成后，宠物系统会从“卡片小游戏”升级为“员工每天能感知到的工作陪伴界面”。
